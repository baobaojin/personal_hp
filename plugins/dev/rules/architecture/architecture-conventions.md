# 架构设计规范

## 分层原则

- controller → service → repository，依赖方向单向向下，禁止跨层调用
- controller：只做参数校验和响应封装，不写业务逻辑
- service：业务逻辑，不直接操作数据库
- repository：数据访问，不写业务逻辑

## 模块划分

- 按业务领域划分模块，不按技术类型（避免 utils 包无限膨胀）
- 模块间通过接口通信，不直接依赖对方实现
- 公共能力抽到 common/shared 模块，不在业务模块间互相依赖

## 设计原则

- **SOLID**：单一职责、开闭原则、依赖倒置
- **KISS**：用最简单的方案解决问题，不过度设计
- **YAGNI**：不实现当前不需要的功能，不为未来预留扩展点
- 重复 3 次再抽象，不要过早抽象

## 可扩展性

- 配置和代码分离，不把配置硬编码在代码里
- 使用策略模式替代大量 if-else
- 核心流程用接口定义，实现可替换
- 数据库表结构变更向前兼容，不做破坏性变更

## 技术选型

- 优先选用团队熟悉的技术，不追新
- 引入新依赖前评估：维护活跃度、包大小、安全漏洞历史
- 记录技术决策的原因（为什么选 A 不选 B）
