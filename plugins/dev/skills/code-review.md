## 流程

**Step 1：确定 Review 范围**
- 如果用户没有指定范围，默认 review 当前 git diff（`git diff HEAD`）
- 如果用户指定了文件或函数，只 review 指定范围
- 先整体扫一遍改动，了解这次改动的目的和规模

**Step 2：分维度审查**

按以下维度逐一检查，每个维度只报告真实问题，不凑数：

**正确性**
- 逻辑是否有 bug（边界条件、空指针、并发问题）
- 数据类型、类型转换是否正确
- 错误处理是否完整（异常有没有被吞掉）

**安全**
- 用户输入有没有校验
- 有没有 SQL 注入、XSS、命令注入风险
- 敏感数据有没有泄露到日志或响应

**性能**
- 有没有 N+1 查询
- 有没有不必要的大对象创建或循环
- 有没有可以缓存但没有缓存的地方

**可维护性**
- 命名是否清晰
- 函数是否过长（超过 50 行考虑拆分）
- 有没有魔法数字或硬编码配置
- 复杂逻辑有没有注释

**Step 3：输出 Review 报告**

按严重程度分级输出：

```
## Code Review 报告

### 🔴 必须修复（影响正确性或安全）
- [文件:行号] 问题描述 → 建议修改方式

### 🟡 建议修复（影响可维护性或性能）
- [文件:行号] 问题描述 → 建议修改方式

### 🟢 可选优化（风格或细节）
- [文件:行号] 说明

### ✅ 总体评价
[一句话总结]
```

**Step 4：等待反馈**
- 如果用户要求修复，直接在代码里改，改完说明改了哪里
- 如果用户有异议，解释理由，不强推

## 合理化借口表

| AI 可能犯的错 | 纠正 |
|---|---|
| 找不到问题就说"代码很好没问题" | 没有完美代码，至少说明检查了哪些维度 |
| 输出几十条鸡毛蒜皮的问题 | 只报告真实影响，风格问题归入可选优化 |
| 不给具体修改建议 | 每个问题必须附带"怎么改" |

## 退出检查

- [ ] 覆盖了正确性、安全、性能、可维护性四个维度
- [ ] 每个问题有文件和行号定位
- [ ] 每个问题有具体修改建议
- [ ] 按严重程度分级输出
