triggers: 帮我排查、这里有 bug、为什么报错、怎么修这个问题、帮我看一下这个错误。

## 流程

**Step 1：收集现象**
- 错误信息/堆栈（必须有）
- 复现步骤（什么操作触发的）
- 期望行为 vs 实际行为
- 最近有没有改过相关代码

如果用户没有提供足够信息，明确说缺什么，等用户补充。

**Step 2：定位问题范围**
- 从报错堆栈找到第一个自己的代码行（不是框架代码）
- 读取相关代码，理解执行路径
- 缩小范围：是数据问题、逻辑问题、还是环境问题

**Step 3：分析根因**

常见根因分类：

| 类型 | 排查方向 |
|---|---|
| 空指针/空值 | 检查数据来源，看哪里返回了 null/None/undefined |
| 类型错误 | 检查数据类型转换，特别是接口边界处 |
| 逻辑错误 | 逐步追踪实际执行路径，对比期望路径 |
| 并发问题 | 检查共享状态、锁的使用 |
| 环境/配置问题 | 检查环境变量、配置文件、依赖版本 |
| 数据问题 | 检查输入数据是否符合预期格式 |

**Step 4：给出修复方案**
- 说明根因是什么
- 给出具体的修改代码
- 说明如何验证修复是否生效

**Step 5：举一反三（可选）**
- 同类问题在其他地方是否存在
- 如何通过测试或代码规范预防这类问题

## 合理化借口表

| AI 可能犯的错 | 纠正 |
|---|---|
| 没有足够信息就猜原因 | 先收集现象，信息不够先问 |
| 给出多个可能原因但不确认哪个 | 要给出最可能的根因，而不是罗列猜测 |
| 只说"检查一下 XX"，不给具体代码 | 修复方案要具体到代码层面 |

## 退出检查

- [ ] 已收集足够的错误信息
- [ ] 定位到了具体的代码位置
- [ ] 说明了根因（不只是现象）
- [ ] 给出了可以直接用的修复代码
- [ ] 说明了如何验证修复生效
