---
name: refactor
description: 对指定代码进行重构，在不改变外部行为的前提下改善代码结构。
triggers: 帮我重构、代码太乱了、优化代码结构、这段代码怎么整理、重构一下。
not_for: 性能优化（用 optimize）、bug 修复（用 debug）、新功能开发。
---

## 流程

**Step 1：理解重构范围和目标**
- 用户想解决什么问题（太长、重复、难懂、难扩展）
- 确认重构范围（单个函数、一个模块、还是跨模块）
- 有没有测试覆盖（没有测试的重构风险更高，需要先说明）

**Step 2：分析现有代码问题**

常见问题识别：

| 问题 | 表现 |
|---|---|
| 函数过长 | 超过 50 行，做了超过一件事 |
| 重复代码 | 相同逻辑出现 2 次以上 |
| 命名不清晰 | 变量名、函数名无法表达意图 |
| 深层嵌套 | if/for 嵌套超过 3 层 |
| 魔法数字 | 硬编码的数字或字符串 |
| 过度耦合 | 一个函数直接操作另一个模块的内部状态 |

**Step 3：给出重构方案**

重构手法（按场景选择）：
- **提取函数**：把一段逻辑提取成有意义名字的函数
- **提取常量**：魔法数字改成具名常量
- **合并重复**：抽取公共逻辑到一处
- **简化条件**：复杂 if-else 改成提前返回或策略模式
- **拆分函数**：一个做多件事的函数拆成多个

**Step 4：执行重构**
- 一次只做一种重构，不混着改
- 改完确认逻辑等价（同样的输入输出相同的结果）
- 如果有测试，确认测试仍然通过

**Step 5：说明改动**
- 改了什么、为什么这样改
- 外部调用方需要注意什么（接口有没有变化）

## 合理化借口表

| AI 可能犯的错 | 纠正 |
|---|---|
| 重构时顺手改了逻辑 | 重构只改结构，不改行为，发现 bug 单独提出 |
| 没有测试直接大刀阔斧重构 | 先说明风险，建议先补测试或小步重构 |
| 一次重构太多地方 | 每次只改一个问题，保持可回溯 |

## 退出检查

- [ ] 确认重构范围和目标
- [ ] 说明了发现的问题
- [ ] 重构后逻辑等价（没有改行为）
- [ ] 说明了外部接口是否有变化
